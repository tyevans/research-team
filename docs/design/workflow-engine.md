# Making the workflow engine produce something

Read out of the working tree at `research_team/domain/workflow.py`,
`research_team/domain/project.py`, `research_team/workflows/`,
`research_team/application/` and `research_team/infrastructure/agent/` on branch
`main` (at `1cc1b78`, after #70 and #71). Line numbers are pointers, not
contracts.

The workflow engine encodes three instructional-design methodologies as data:
33 stages across three presets, with declared artifacts, gates, reviewer roles,
a 21-check library and a maturity ladder. It has never produced a course. This
document says what the two missing pieces are, what they must contain, and —
the part I expect to be least welcome — how much of the missing work is not
code.

**How the load-bearing claims were checked.** Most of the argument below rests
on absences, and an absence is the easiest thing to get wrong by reading too
little. Every one was checked by a query you can rerun, and the queries are
written out rather than described:

- *No prompt library exists.*
  `find . -type d -name 'prompts*' -not -path './.git/*'` returns exactly one
  hit, `.venv/lib/python3.13/site-packages/langchain_core/prompts`. There is no
  `prompts/` in the repository.
- *There are 38 distinct references and 49 uses.*
  `grep -rhoP 'prompt_ref\s*=\s*"[^"]+"' research_team/ | grep -oP '"[^"]+"' | tr -d '"' | sort -u | wc -l`
  → 38; without `-u` → 49. So eleven references are used twice, and §4 is about
  which eleven.
- *Nothing reads a `Generator` or a `Critic`.*
  `grep -rnE '\.critic\b|\.generator\b|getattr\(.*"critic"|getattr\(.*"generator"' --include='*.py' research_team/ | grep -v workflows/`
  returns two lines, `checks.py:1099` and `:1100`, both inside
  `_self_review_separation`, and both only to compare the two for *inequality*.
  The entire "who writes, who reviews" half of the data model is inert.
- *Nothing reads the loop machinery.* The same grep over
  `loop_policy|max_iterations|convergence_check|adversarial_second_pass|over_generate_factor|taxonomy_binding|require_citation`
  outside `workflows/` returns only the field declarations in
  `domain/workflow.py` itself. `reviewer_role` escapes to
  `course.py:324` → `presenters.py:382`, for display on the stage rail, and
  nowhere else.
- *`advance_stage` is the only motion, and it moves forward by one.*
  `domain/project.py:_advanced` (line 293) computes `ids[at + 1]` and raises
  `CommandRejectedError` for anything else. §3 turns on this and it is the
  finding I most want a reader to check personally.

**What I did not check, and cannot.** Nothing here has been run against a
populated database, because there is nothing to run: no prompt is resolved, no
stage is driven, and no course has ever been generated by this system. The
whole test suite passes and that fact carries no information about whether any
of this works — see `CLAUDE.md` on read models, and §8 of `landing-page.md`
beside this file for what "it works on my fresh database" cost the last time.
Every cost estimate in §7 is arithmetic over the preset data, not a measurement.
Where I say "measured", it was measured; everywhere else it was reasoned.

Short version, so the rest reads as argument rather than suspense:

- **The prompt library is not a coding task.** It is 38 pieces of
  instructional-design writing, each of which has to be right in a way only
  somebody who knows the methodology can judge. The loader is an afternoon; the
  content is weeks. §2 and §8.
- **A driver may never advance a stage.** Not "should not by default" — never,
  under any flag it can reach. Everything else a driver would do is legitimate
  and useful. §3.
- **Most of the "validated but unexecuted" machinery is not merely unexecuted;
  it is unrepresentable.** `amend_upstream`, `send_back`, `halt` and
  `approve_with_edits` are all in the `Decision` literal and none of them can be
  written to the log: the only event is `StageAdvanced`, which goes forward.
  Executing `LoopPolicy` is a domain change, not a driver. §3.4.
- **Sharing prompts across presets is already happening in the shipped data** —
  eleven of 49 references — and it is safe in exactly the pattern the data
  already uses. Sharing between a generator and its critic is not "anticipated";
  `checks.py:1110` **forbids** it, at invariant severity. §4.
- **The smallest useful first increment is `ubd.pure`, six stages, generators
  only, no critics.** §5.

## 1. What is built, and the exact shape of the two holes

The skeleton is genuinely good and it is worth being precise about how far it
goes, because "mostly built" and "0% built" are both wrong.

**Built and tested.** The discriminated stage union (eight classes, so a screen
that generates its own candidates is untypeable rather than merely invalid);
`problems()` with eleven validation rules, run at import so a malformed preset
fails on test collection; artifact paths and frontmatter (`artifacts.py`); the
21 checks the presets bind, all implemented, plus one registered and unused
(`ubd.uncoverage`); `stage_exit.review_stage` running a stage's checks at the
moment somebody is asked to let it go, writing a findings artifact and attaching
it to the approval; `StageMiddleware` filtering the bound tool list down to what
the stage claims; `advance_stage` with its `ask` floor; `course_progress` and
the stage rail.

That is more than a skeleton. A human sitting in a session on a project with a
preset selected really does get a narrowed tool list, a stage-specific artifact
block naming the files they owe and the frontmatter those files need, a check
report when they propose to advance, and a rail showing where they are.

**Hole 1: the prompt library.** Every `_Authored` stage carries
`Generator(role=…, prompt_ref=…)` and eighteen of them also carry a `Critic`.
There is no `prompts/` directory, no resolver and no loader. The consequence is
visible in `composition.py:621`, which is where a resolved prompt would go and
does not:

```python
StageMiddleware(
    stage,
    managed_tools=managed_tools_for(preset.stages) - {ADVANCE_STAGE_TOOL},
    instructions=(
        stage_artifact_instructions(preset, stage)   # which files, what frontmatter
        + WORKFLOW_PROMPT                            # how the gate works
        + component_guidance(stage.outputs)          # widget syntax, where relevant
    ),
)
```

Three terms, all of them *mechanical*. A model working `ubd.stage1.desired_results`
is told to write `/course/02-intent-transfer-goal.md` with provenance
frontmatter. It is told nothing about transfer goals, nothing about the stem
"Students will understand that", nothing about why an essential question that
can be answered with a date is not an essential question — even though
`shared.format_conformance` will reject its work for exactly that, after the
fact, with a regex. **The instructional-design intelligence of the whole system
currently exists only as post-hoc rejection.** `stage_middleware.py:60` states
the gap in its own docstring ("Notably absent: the prompt"), which is the
politest possible way to leave a hole this size.

**Hole 2: the driver.** Nothing turns "this project is at stage X" into a model
turn. `TurnSupervisor` runs a turn when a human sends a message; `AutoResearchDriver`
runs rounds against a topic queue; neither knows a stage exists. A course is
produced today by a human opening a session, typing "do this stage", reading
what came back, and typing again — fifteen times for the hybrid, with an
approval interrupt at each boundary.

## 2. The prompt library

### 2.1 What a prompt must *not* say

The contract is easier to state as negative space, because three other things
are already injected into the same system message and a prompt that repeats them
is worse than one that omits them.

A stage prompt must not name its output paths, its artifact types, or its
frontmatter — `stage_artifact_instructions` derives all of that from
`stage.outputs`, and its docstring says why: "so a preset edit cannot leave the
prompt describing files nothing looks for". A prompt that hardcodes
`/course/05-evidence-spec-performance-task.md` is a prompt that breaks silently
the next time somebody inserts a stage.

It must not explain the gate. `WORKFLOW_PROMPT` does that, in words chosen to
say the thing that matters ("expect to wait and expect to be refused").

It must not carry widget syntax. `component_guidance(stage.outputs)` decides
that from the declared outputs, and its own docstring makes the argument for
why blanket injection is wrong: a stage writing source claims has no use for two
kilobytes of widget reference, and a prompt carrying it anyway teaches the model
that most of its instructions do not apply to it.

It must not name the current stage. `stage_prompt` already emits
`## Current stage: {name} ({id})`.

It must not list its tools. `StageMiddleware` withdraws what the stage does not
claim, and the module docstring is emphatic that this is the point: "Telling it
'you are in the draft stage, do not advance yet' is a suggestion; a model that
never sees `advance_stage` bound cannot call it."

**What is left is the only thing a prompt is for: the methodology.** What a
transfer goal is and how it differs from an understanding. Why GRASPS has six
slots and what a degenerate `situation` looks like. What "three disjoint
analysts" means and why the learner route must not be written by the same pass
that wrote the discipline route. Why an ADDIE objective may not use the verb
"know". That content does not exist anywhere in this repository except as
prose in `docs/research/course-design/`, and as regexes in `checks.py` that
reject its absence.

### 2.2 Shape

A prompt is a markdown file with frontmatter, for the same reason artifacts are:
the parser exists (`artifacts.parse_frontmatter`), the viewer renders it, and
inventing a second format would be a second thing to maintain.

```
prompts/ubd/stage1_generate.md

---
prompt_ref: prompts/ubd/stage1_generate
version: 1
kind: generator
methodology: ubd
intended_for:
  - ubd.pure/ubd.stage1.desired_results
summary: >
  Desired results — transfer goals, understandings, essential questions.
---

You are a curriculum designer working the first stage of Understanding by
Design...
```

`prompt_ref` is stated in the file and must equal its own path minus `.md`. That
looks redundant and is the whole of the loader's integrity check: a file moved
without its frontmatter updated is caught at load, not by a run that silently
gets the wrong prompt.

`kind` is `generator` or `critic`, and it is enforced against the field that
referenced it. A `Critic.prompt_ref` pointing at a `kind: generator` file is the
self-review failure arriving through the filesystem instead of through the
preset, and `checks.py`'s invariant would not catch it because the two
`prompt_ref` *strings* differ.

`intended_for` is a list of `preset_id/stage_id`. It is documentation for a human
and an assertion for a test (§2.5); it is deliberately **not** consulted at
resolution time, because a preset that references a prompt is the authority on
what that prompt is for, and a second gate that could disagree would eventually
disagree.

`role` is *not* in the frontmatter. It is on the `Generator` in the preset, and
it belongs there: `prompts/ubd/stage2_generate` is used by two presets with
different role strings (`"assessor"` in `ubd.pure`,
`"assessor — think like an assessor before designing lessons"` in the hybrid),
which is a deliberate difference the hybrid makes and a prompt file has no
business overriding. The resolver composes them; the prompt does not contain
either.

### 2.3 Resolution and loading

```python
# research_team/application/prompts.py

class PromptLibrary(Protocol):
    def resolve(self, ref: str, *, kind: Literal["generator", "critic"]) -> str: ...
```

Loaded once at composition, from a directory on disk, into a frozen mapping.
Not lazily per turn: a missing prompt is a broken installation and the useful
moment to learn that is startup, exactly as `problems()` validates presets at
import rather than at selection.

**Missing refs are a startup failure, not a fallback.** The tempting
alternative is "resolve to empty and carry on", and it is the same mistake
`composition.py:503` already documents for a missing preset — running ungated
"is at least the behaviour the project had before it chose". That reasoning does
not carry over. An ungated run is visibly ungated; a stage running with an empty
prompt is *indistinguishable from today*, which is to say it produces
methodology-free output that passes every structural check and is wrong in the
one way nobody can see. The composition root should refuse to build with a
preset whose prompts it cannot resolve, and say which ref and which stage.

The resolved text joins `composition.py`'s existing concatenation as one more
term, placed first:

```python
instructions=(
    prompts.resolve(stage.generator.prompt_ref, kind="generator")
    + role_line(stage.generator)          # role, taxonomy_binding, over_generate_factor
    + stage_artifact_instructions(preset, stage)
    + WORKFLOW_PROMPT
    + component_guidance(stage.outputs)
),
```

`role_line` is small and is the place the three inert `Generator` fields finally
get read. `taxonomy_binding` matters most: `blooms_revised` and `six_facets` are
named-never-unioned precisely because they are incompatible, and a stage that
does not tell the model which one it is working under will get whichever the
model prefers.

A `ScreenStage` has no generator by construction, so its prompt is its critic's.
A `FieldStage` has neither and must resolve nothing — an agent cannot execute it
at all, and `stage_artifact_instructions` already emits "This stage produces no
artifact of its own" for the zero-output case.

### 2.4 Versioning, and what happens when a prompt changes mid-run

This is the question in the brief with a wrong answer that looks right, so it is
worth working through what the system already does.

`WorkflowSelected` records `preset_id` and `preset_version` and explicitly
refuses to record the preset by value: "A preset is hundreds of lines of prompts
and checks, and copying it into the log would both bloat every snapshot and
freeze a typo forever." `composition.py:519` then tolerates a version mismatch
with a log line and runs under what is *installed*, not what was selected,
because "refusing to run would strand every project mid-flight on an edit".
`artifacts.py` writes `preset` and `preset_version` into every artifact's
frontmatter.

So the existing posture is: **presets are content, content gets edited, the run
proceeds under the installed revision, and the artifact frontmatter is the
record of which revision produced each file.** Prompts are content of exactly
the same kind and should inherit exactly that posture.

The obvious move is to give each prompt its own version, pin it in the preset
(`prompt_ref: prompts/ubd/stage1_generate@3`), and record the pin. **Do not do
this.** It buys a precision nothing consumes and costs a class of failure the
system does not currently have: a preset edited to add a stage now also has to
have 38 pins reconciled, and a pin that points at a version no longer on disk is
a run that cannot start, which is the strand-mid-flight failure the version
mismatch was deliberately softened to avoid. Prompt versions are not
independently meaningful anyway — a prompt is only ever used by the stages that
reference it, and the stage list is what the audit trail is gated by.

**The proposal instead: the preset's version covers its prompts.** Editing any
prompt a preset references is editing that preset, and bumps `Preset.version`.
This is a discipline rather than a mechanism, and a discipline nobody can check
is a wish, so it needs one thing to make it real:

**Record a prompt digest on the artifact.** `stage_artifact_instructions`
already writes `preset` and `preset_version` into frontmatter. Add
`prompt_digest`: a short hash over the exact resolved text the stage ran under.
Then "which revision of the workflow produced this file" is answerable even when
somebody edited a prompt and forgot to bump the version, which is the case that
will actually happen. It is four lines, it needs no new event, and it is the
difference between a version field that is true and one that is aspirational.

**Mid-run, a prompt change lands at the next turn and that is correct.** A
stage already advanced is settled; its artifact carries the digest of the prompt
that wrote it. A stage in flight picks up the new text on its next turn, which
is the same behaviour a preset edit already has, and the same behaviour
`AutonomyPolicy` has ("a change lands on the next call — including partway
through a turn already in flight"). The alternative — freezing the resolved
prompt for the duration of a stage — would mean the fix you just made to a
prompt does not apply to the run you made it for, which is the opposite of
useful when the run in front of you is how you discovered the prompt was wrong.

### 2.5 Testing

Three tests, and only the first is about the loader.

**Every referenced prompt resolves, and resolves to the right kind.** Parametrised
over `PRESETS`, walking every stage's generator and critic. This is the test that
fails when somebody adds a stage and forgets the prompt, and it is the reason to
put `kind` in the frontmatter.

**No prompt file is orphaned.** Every file under `prompts/` is referenced by some
preset. An unreferenced prompt is either a preset edit that lost its stage or a
prompt written against a stage that was renamed, and both look like nothing.

**`intended_for` agrees with the presets, in both directions.** This is the one
that earns its place: it is a redundant declaration whose only job is to
disagree, exactly like `FieldGate.gates_promotion_from`, whose docstring already
argues the general case — "Naming the rung here gives the two facts something to
disagree about". A prompt written for UbD Stage 1 and quietly referenced by an
ADDIE stage is §4's trap, and this test is where it is caught.

What no test can do is tell you whether a prompt is any *good*. §6.

## 3. The driver, and the human gate

### 3.1 What a driver may do unattended

A driver is a loop that runs turns against a project that has a preset and a
current stage. Precisely:

- **Start a turn** against the current stage, with the stage's tool filter and
  resolved prompt, when the previous turn ended and the stage's declared
  artifacts are not all present.
- **Stop** when they are all present, or when a budget is exhausted, or when the
  same turn has failed `max_consecutive_failures` times — `Budget` in
  `domain/auto_research.py` is the shape, and its argument for counting rounds
  and turns separately applies here unchanged.
- **Run the stage's checks** — `stage_exit.review_stage` is already pure over
  the course directory and can be called without an approval in flight — and
  feed the findings back into the next turn. This is the single highest-value
  thing a driver does, and it costs nothing: the checks are graph and schema
  queries, none requires a model call.
- **Propose** `advance_stage`, which raises the interrupt and waits.
- **Report** what it did, on the existing SSE feed, as `FileWritten` and
  `StageAdvanced`, both of which already reach the browser.

### 3.2 What a driver may never do

**It may never make the stage boundary pass without a human.** There are two
routes and both must be closed.

The first is calling `advance_stage` with the approval auto-approved. The floor
in `TOOL_FLOORS` is a *floor*, not an override — `AutonomyPolicy.level_for`'s
docstring says so and `relax_all(include_stage_gates=True)` is a supported,
deliberate act with an HTTP route in front of it (`AllowAll` in `web/app.py`).
That option exists for a human who has decided they are the review, and it is
right that it exists. **A driver must not be able to reach it.** Concretely: the
driver holds no reference to `AutonomyPolicy` and never calls `set` or
`relax_all`. `auto_research.py:26` already states this rule for the run loop —
"a loop that could lower its own floors would make `TOOL_FLOORS` a suggestion"
— and it is the same rule.

The second route is subtler and is the one I would expect an implementation to
get wrong: **a driver must not call `Project.execute(AdvanceStage(...))`
directly.** The domain command is not gated; the *tool* is. `ProjectWorkflow`
exists (`persistence/project_workflow.py`) and a driver holding a repository
could advance a stage without any tool call, any approval, any interrupt, and
any `ToolCallDecided`. Nothing in the type system prevents it and no existing
test would fail. The driver's only route to the boundary must be proposing the
tool call and letting the interrupt happen, and that should be asserted by a
test that drives a stage to completion and checks that no `StageAdvanced` was
appended.

**Corollary: a driver cannot finish a course.** It finishes a *stage*, then
stops and waits for a person. Fifteen human decisions for the hybrid, six for
`ubd.pure`. That is not a limitation of the driver; it is the product. If the
owner wants a course produced without fifteen reviews, the honest options are to
run a shorter preset or to turn `advance_stage` to `auto` by hand and own the
consequence — not to build a driver that quietly does it.

### 3.3 What executing the critic machinery means

`Critic.separate_context: True` is on every critic in every preset, and its
docstring is unambiguous: "MUST stay true wherever a critic gates a generator. A
critic that has seen the generating rationale is reviewing the argument, not the
artifact."

There is exactly one mechanism in this codebase that gives a model a fresh
context and returns only a conclusion: the `task` tool and the subagent in
`delegation.py`. **So a critic is a subagent**, given the critic prompt, the
artifact paths, the criterion document, and nothing from the generating turn.
That is a good fit and it is also the expensive one, and `delegation.py`'s own
docstring is the honest source on the cost:

> Anthropic reports a large quality win […] but also that token spend alone
> explained most of the performance variance — much of the win is paying more,
> not organising better — at three to ten times the tokens of a single agent.

It also carries a warning that lands here: subagents that each produce part of an
artifact "make conflicting implicit decisions the parent must then reconcile",
and the guidance steers delegation toward *investigation*. A critic is
investigation — it reads and returns a verdict — so it is on the right side of
that line. A generator delegated to a subagent would be on the wrong side, and
should not be.

`adversarial_second_pass: True` (three stages in the hybrid, one each in the
pure presets, and the default on every `ScreeningCritic`) means a second
subagent turn against the same artifact with the instruction to argue the
opposite. `require_citation: True` means the verdict must cite a clause of the
`criterion_doc` — and `shared.verdict_citation` already checks that, at invariant
severity, refusing outright rather than reporting. So the critic machinery is not
free-floating: its output is checked by machinery that exists.

**Failure modes worth naming before they are met.** A critic that returns
"looks good" is indistinguishable from a critic that read nothing, and the only
defence is `verdict_citation` — which applies to screens, where a `VerdictLedger`
is a declared output, and to nothing else. Nine of the eighteen critics produce
no artifact at all; their verdicts exist only as a subagent's return string in
the parent's context, which is not in the log. **A critic whose findings are not
written to a file did not happen, as far as any audit is concerned.** If critics
are executed, each should write its findings to a path — the `findings_path`
convention in `stage_exit.py` is the precedent — or the run will produce a
course that claims eighteen reviews and can evidence two.

### 3.4 The part that is not a driver at all

This is the finding I least expected and it changes the size of the question.

`Decision` is `approve | approve_with_edits | amend_upstream | send_back | halt`.
Gates declare which they permit; `course.py` projects them onto the rail;
`Amendments.emits_to` says where an `amend_upstream` may go, and `problems()`
validates that those targets are earlier stages.

**Four of the five decisions cannot be recorded.** The project aggregate has one
stage event, `StageAdvanced`, with `from_stage`, `to_stage`, `decided_by` and
`gate_decision`. `_advanced` computes `ids[at + 1]` and refuses everything else
by name, including going back — "revision is real and necessary, but it is an
amendment emitted *to* an earlier stage rather than a return to it". And
`gate_decision` is not a `Decision`: `build_workflow_tools` passes the model's
free-text `rationale` into it. There is no field anywhere that holds which of the
five decisions a reviewer made.

So `LoopPolicy.max_iterations`, `LoopPolicy.convergence_check`,
`Amendments.emits_to`, `MaturityGate.rungs` as a ladder to climb, and
`DecisionGate`'s halt are not "validated data that a driver would execute". They
are validated data for which **no execution is expressible**. Building the
missing half means new domain events (an amendment recorded against an earlier
stage; a halt; a rung promotion), new commands, and — the expensive one — an
answer to what a project's `current_stage` means while an amendment against an
earlier stage is outstanding.

That is a second design document, and it should not be smuggled into a driver.
The driver in §3.1 is complete and useful without it: it drives forward, one
stage at a time, and a reviewer who wants to send work back does so by refusing
the approval and saying why, which works today. **What must not happen is a
driver that implements looping in process state** — a retry counter living in
the supervisor, converging or not converging with nothing in the log — because
that reproduces `LoopPolicy` as a thing only the running process knows, and
`ResearchSupervisor`'s docstring already refuses that class of invention.

I would state it in the preset data too: `LoopPolicy` and `Amendments` should
carry a line saying they are declared and not yet executed. Data that looks
executed and is not is how the next reader loses a day.

## 4. Sharing prompts across the three presets

The brief asks whether the presets should share prompts where their stages
overlap, and says `checks.py:1110` suggests sharing is anticipated. **It says
the opposite,** and the correction matters because it is the sharp edge.

### 4.1 The check forbids sharing; it does not anticipate it

```python
if critic.prompt_ref == generator.prompt_ref:
    reasons.append(f"critic and generator share the prompt {critic.prompt_ref!r}")
```

That is inside `_self_review_separation`, registered with
`fixed_severity="invariant"`. Per `stage_exit.py`, an invariant "refuses before
the human is consulted" — the run stops. So a shared `prompt_ref` between a
generator and its critic is a hard failure, listed alongside "it reviews its own
stage". It is a rule about *generator ↔ critic* sharing, within one stage. It says
nothing about sharing across stages or across presets, and reading it as
permission is reading a lock as a door.

Verified in the shipped data: 18 stages carry both a generator and a critic, and
in none of them do the roles or the prompt refs coincide. The invariant has never
fired, and is bound at exactly one stage across all three presets
(`hybrid.default/tyler.step2.philosophy_screen`) — which is `BACKLOG.md` B22's
complaint, and B22's proposed fix (assert it in `stage_exit` for every stage with
both, whether the preset asked or not) becomes considerably more urgent once
prompts exist, because the failure it guards is invisible in the output.

### 4.2 Where sharing is already real, and safe

Eleven of the 49 references are used twice. Every single reuse is
**cross-preset**, never within one preset, and always between the hybrid and the
pure preset it lifted the stage from:

| Prompt ref | Shared by |
|---|---|
| `prompts/addie/gap_framing`, `gap_critique` | `hybrid.step1.framing` ↔ `addie.a1.intake_gap_framing` |
| `prompts/addie/storyboard`, `storyboard_critique` | `addie.d5.storyboarding` in both |
| `prompts/addie/build`, `qa` | `addie.v1.build` in both |
| `prompts/addie/implement` | `addie.i1.implementation` in both |
| `prompts/ubd/stage2_generate`, `stage2_critique` | `ubd.stage2.evidence` in both |
| `prompts/ubd/stage3_generate`, `stage3_critique` | `ubd.stage3.learning_plan` in both |

Nine of the eleven share a *stage id* as well as a prompt: the hybrid does not
re-describe ADDIE's development phase, it names `addie.v1.build` and reuses it.
That is the correct pattern and it should be preserved rather than
rationalised: **the unit of sharing is a stage, not a piece of instructional
work that resembles another piece.** When the hybrid takes ADDIE's storyboarding
stage, it is running ADDIE's storyboarding stage, and one prompt is right because
there is one stage.

### 4.3 Two traps inside the sharing that already exists

Even within that safe pattern, two of the shared refs are bound to stages whose
declarations differ, and a prompt author who does not know will write something
wrong.

**`prompts/addie/storyboard` has different outputs and a different scope on each
side.** In `addie.pure` the stage is `scope_level="asset"` and declares one
output, `ProductionSpec`. In `hybrid.default` it is `scope_level="module"` and
declares two, `ProductionSpec` and `StyleGuide` — because the hybrid has no
`addie.d4.treatment` to have produced the style guide earlier. A prompt that says
"produce a production spec, following the style guide you were given" is correct
in one preset and wrong in the other.

**`prompts/addie/gap_framing` is bound to stages with materially different
artifact sets.** `hybrid.step1.framing` emits `ContextProfile` and
`ConstraintRegister` (the hybrid has no separate audience stage);
`addie.a1.intake_gap_framing` emits `SourceClaim`, `ContestedQueue` and
`OpenQuestion` and defers the profile to `addie.a3`. Same prompt, five outputs
versus six, three of them disjoint.

The mitigation is the rule from §2.1, and this is why that rule is load-bearing
rather than tidy: **a shared prompt must never name its outputs.**
`stage_artifact_instructions` names them, correctly, per stage. A prompt that
teaches the *method* — what a gap statement is, why the business metric must be
measurable, why "options considered" must include a non-training option — is
correct in both. A prompt that teaches the *deliverable list* is correct in at
most one. The test in §2.5 catches the reference being added; only the discipline
catches the content drifting.

### 4.4 Where the overlap is apparent and collapsing it would be a disaster

Four stages across the three presets produce `Intent`, under four different
prompts. They look like the same stage. They are not, and the checks bound to
each say so precisely:

| Stage | Prompt | Taxonomy | Subtypes | Format check |
|---|---|---|---|---|
| `tyler.step1b.candidates` | `prompts/tyler/candidates` | none | `candidate` | provenance to `SourceDossier`; `over_generate_factor=5` |
| `ubd.stage1.desired_results` | `prompts/ubd/stage1_generate` | none | `transfer_goal`, `understanding`, `essential_question`, `knowledge`, `skill` | stem `"Students will understand that"`; rejects essential questions matching `^(What year\|Who was\|How many…)` |
| `addie.d1.objective_formulation` | `prompts/addie/objectives` | `blooms_revised` | `terminal_objective`, `enabling_objective` | verb denylist including `know` |
| `hybrid.step4.intent_spec` | `prompts/hybrid/intent_spec` | `hybrid_per_subtype` | none | *both* the UbD stem rule and the ADDIE verb denylist |

A UbD understanding is a sentence a student cannot be examined on directly and
that the whole unit exists to make defensible. An ADDIE terminal objective is a
behaviour with a condition and a criterion, coded to a Bloom's level that its
assessment items must match (`shared.taxonomy_distribution` with
`must_match_parent: Intent.bloom_level`). A Tyler candidate is a deliberately
over-generated proposal that two screens will cut by 60–85%
(`shared.prune_ratio` expects 0.15–0.4 survival) and whose value is that most of
them die.

**Collapsing these into one `prompts/shared/objectives` would make each
methodology produce another's output while every structural check still passed.**
The matrix density check would pass, the orphan check would pass, the coverage
check would pass — because they are all graph queries over `Intent`, and the
collapse does not change the graph. The one thing that would catch it is
`format_conformance`, and it catches only the surface: a well-formed ADDIE
objective written where a UbD understanding belonged fails no regex, because the
UbD stem rule is bound to `Intent.understanding` and the collapsed prompt would
not have produced that subtype at all. The failure would present as a course
that is internally consistent, passes its gates, and is not the methodology the
user selected.

Note that `hybrid.step4.intent_spec` is the *correct* way to combine two
traditions' objective work: a fourth prompt, written deliberately, with
`taxonomy_binding="hybrid_per_subtype"` and both sets of format checks bound. It
is more work than sharing, and it is the work.

The same argument applies, more briefly, to three other apparent overlaps:
`ubd.stage3.organization` / `tyler.step6.organization` / `addie.d3.course_map`
are all sequencing and are three prompts (Tyler's organization is about
continuity, sequence and integration of *threads* over a program, with a
`recurrence` check demanding three occurrences; ADDIE's course map is a module
ordering under a seat-time budget); and `addie.d2.assessment_design` /
`ubd.stage2.evidence` are both evidence-before-instruction and are as different
as a Bloom's-matched item bank and a GRASPS performance task.

### 4.5 The rule

**Share a prompt when two presets reference the same stage id. Never otherwise.**

That rule is mechanical, it is checkable, and it exactly reproduces the eleven
reuses already in the data — with `prompts/addie/gap_framing` as the one
exception, shared across `hybrid.step1.framing` and
`addie.a1.intake_gap_framing`, which is a deliberate rename and should carry a
comment saying so. A test asserting "a `prompt_ref` used by two stages with
different ids is either forbidden or explicitly allowlisted" would hold the line
and take ten lines.

## 5. The smallest useful first increment

**`ubd.pure`, all six stages, generator prompts only, no critics, no driver.**

The reasoning, in order of how much each choice saves:

**One preset, not three.** `ubd.pure` over `hybrid.default` because it has six
stages against fifteen, `produces="design"` so it terminates before production
and the ADDIE build/deploy prompts are out of scope entirely, and it is the
preset with the tightest published methodology — Wiggins and McTighe wrote the
design standards down, so a prompt author has a source and a reviewer has a
rubric. `addie.pure` is the wrong first choice because
`has_value_filter is False` and it runs to spine 10: it produces materials and
tracking packages, which is the largest surface and the least interesting output.

**All six stages, not one.** A single stage proves the loader and proves nothing
about the workflow, because the thing that makes this system worth building is
that stage 2 constrains stage 3. One stage in isolation is a prompt in a text
box.

**Generators only, no critics.** Ten of the eighteen critics are the cost driver
(§3.3, §7), and their value depends on `criterion_doc` files
(`ubd.design_standards.stage1` and friends) that also do not exist anywhere in
the repository — `grep -rn 'design_standards' research_team/ | grep -v workflows/`
returns nothing. Writing four UbD critic prompts *and* the design-standards
documents they cite is a second project. Without critics the run is weaker and
says so: the stage rail already shows what each stage produced, and a course
built without its critics should be visibly labelled as such rather than quietly
equivalent.

**No driver.** A human prompting six stages by hand is how you find out whether
the prompts are any good, and it is the only way to find out cheaply. A driver
built before the prompts are trustworthy automates the production of bad
courses. The driver is increment three.

The order after that: (2) the four UbD critic prompts and their design-standards
documents, with critics as subagents; (3) the driver from §3.1, bounded, that
still cannot advance a stage; (4) the ADDIE prompts, which unlock `addie.pure`
and — with UbD's already written — most of the hybrid; (5) `hybrid.step4.intent_spec`,
`prompts/hybrid/intent_critique`, `prompts/hybrid/outcomes` and the Tyler set,
which complete the hybrid. B22's engine-level invariant should land with (2),
before there are eighteen critics to get wrong.

## 6. How you would know the prompts are any good

Four signals, weakest first, and the honest answer is that only the last one is
real.

**The checks pass.** Cheapest and least informative. Every check in the registry
is a graph or schema query — `Check`'s docstring says so — so they measure
structure. A course that passes all 21 checks can still be a bad course, and §4.4
is the specific way: a well-formed artifact of the wrong methodology passes
nearly everything.

**Golden runs.** One small corpus, run through the six stages, artifacts
committed. Then a prompt edit shows as a diff. This catches regressions and
detects nothing about whether the baseline was good, and it is expensive to
maintain against a nondeterministic model. Worth doing at the level of "the
artifact has the right shape and the right subtypes", not "the text is stable".

**A/B against a stage's checks.** Run a stage under two prompt revisions, count
findings. Real signal, narrow: it tells you which prompt produces fewer
structural complaints, which is not the same as which produces a better course.

**The `approve_with_edits` delta, and this is the one that matters.**
`synthesis-generic-workflow.md:689` already worked this out and it is worth
quoting because it is the project's own answer:

> `approve_with_edits` — reviewer patches the artifact inline and proceeds.
> Patches are recorded as a diff, not silently merged, so the delta between
> machine output and human-corrected output is measurable over time. **That delta
> is the best available signal for which stages need better prompts.**

The filesystem is event-sourced, so every version of every artifact is already
recoverable by scrubbing — the raw material exists. What does not exist is the
decision that says "this edit was a reviewer correcting the machine": per §3.4
there is no `approve_with_edits` anywhere in the domain, and `gate_decision` is
free text. **So the best available signal is unavailable, and making it available
is a small domain change** — a decision field on `StageAdvanced`, defaulting to
`approve` for case-1 schema evolution — that is worth doing early, because it is
the difference between improving the prompts from evidence and improving them
from opinion. It is also, notably, much cheaper than executing `LoopPolicy`, and
buys more.

Below all four: **somebody who knows the methodology has to read the output.**
There is no substitute and pretending otherwise is how a project ships a course
generator that produces confident nonsense.

## 7. What this costs in model calls per course

Arithmetic over the preset data, not a measurement. Assume a generator stage
takes 2–4 turns (draft, read the check findings, revise) — the low end of that
is optimistic and there is no evidence for either end.

| | `ubd.pure` | `addie.pure` | `hybrid.default` |
|---|---|---|---|
| Stages | 6 | 12 | 15 |
| With a generator | 6 | 11 | 12 |
| With a critic | 4 | 6 | 10 |
| Adversarial second pass | 1 | 1 | 3 |
| Declared output files | 23 | 33 | 51 |
| Human approvals (one per boundary) | 5 | 11 | 14 |

**Generators only, first increment:** 6 stages × 2–4 turns = **12–24 model calls**
for `ubd.pure`.

**With critics:** each critic is a subagent turn, each adversarial pass another,
and a critic that finds something costs the generator a revision turn. UbD:
+4 critics +1 adversarial +~4 revisions ≈ **21–33 calls**. The hybrid with
everything: 12 generators × 2–4 = 24–48, plus 10 critics, plus 3 adversarial,
plus revisions ≈ **50–80 model calls**, at 3–10× tokens for the subagent portion
per `delegation.py`.

**Two things the table does not show and should.** First, `over_generate_factor`
is 5 at `tyler.step1b.candidates` and `ubd.stage1.desired_results` and 2 at
`addie.d2.assessment_design`: those stages are *meant* to produce five times what
survives, so they are the long turns, and a context-window failure is likeliest
there. Second, the wall-clock cost is not the model. Fourteen human approvals on
the hybrid, each a real review of real artifacts, is the actual price of a course
— and the whole point of the design. A run that takes 80 model calls on a local
endpoint and a week of a reviewer's attention is not a run whose model calls are
the expensive part.

## 8. Honest scale

**The loader, the resolver, the frontmatter, the tests and the composition wiring
are perhaps two days.** The `instructions=` concatenation in `composition.py:621`
is one term longer. The driver in §3.1 is another two or three days, modelled on
`AutoResearchDriver`, which already has the budget, the stop reasons and the
supervisor shape.

**The 38 prompts are not that.** Each one has to teach a methodology-specific
discipline to a model well enough that its output survives a domain expert
reading it — the difference between a transfer goal and an understanding, why a
GRASPS `situation` reading "a real-world scenario" is a failure
(`required_field_nondegenerate` names that exact phrase in its
`generic_phrases`), what makes an ADDIE distractor plausible rather than silly.
Most of them also want a criterion document to cite, and those do not exist
either: `ubd.design_standards.stage1/2/3/overall`, `tyler.philosophy_statement`,
`tyler.learning_theory_statement`, `tyler.source_bias_profiles`,
`tyler.organization_criteria`, `addie.intervention_criteria`,
`addie.objective_criteria`, `addie.item_quality_criteria`,
`addie.task_analysis_criteria`, `addie.style_guide`, `addie.qa_criteria` —
**fourteen** named criterion documents referenced across the three presets, zero
present in the repository. (Checked with a walk over every `Critic.criterion_doc`
and every check param named `doc`; then
`grep -rln 'philosophy_statement\|intervention_criteria\|qa_criteria' --include='*.md' --include='*.py' .`,
which finds only the preset modules that name them and the synthesis document.)
Two of them, `tyler.philosophy_statement` and
`tyler.learning_theory_statement`, are subject to
`tyler.criterion_doc_authored` with `require_human_signature: True` and
`forbid_derivation_from: SourceClaim`, which is to say **the system explicitly
requires a human to have written them and forbids generating them.**

Writing 38 prompts and 14 criterion documents at a standard a domain expert
would sign is, plainly, **several weeks of instructional-design work, not a
coding task.** It is also the work that makes everything else worth having: the
engine's whole value proposition is that it encodes methodology, and the
methodology is currently absent. `docs/research/course-design/` is the raw
material — `tyler-model.md`, `backward-design.md`, `addie.md` and
`synthesis-generic-workflow.md` are substantial and were clearly written by
somebody who did the reading — so this is compilation rather than research. That
is a real discount and it is not a discount to zero.

**The nearest good version, if that is more than the owner wants to spend:** do
`ubd.pure` only, six generator prompts and no criterion documents (UbD's design
standards are published and can be cited as a criterion document written once,
by hand, for all three stages). Six prompts and one document is a week rather
than a month, it produces a complete design-level course, and it answers the
question the whole project is actually asking — does an encoded methodology
produce better output than an unencoded model — with a real artifact instead of
an estimate. If it does not, the other 32 prompts were never worth writing.

## 9. What I am not proposing, and what I could not decide

### Not proposing

- **Per-prompt versions pinned in the preset.** §2.4. The preset's version covers
  its prompts; a `prompt_digest` on the artifact frontmatter makes that honest.
- **A fallback for an unresolvable prompt.** §2.3. Startup failure. An empty
  prompt is indistinguishable from today, which is the failure.
- **Prompts that name their output paths, artifact types or frontmatter.** §2.1.
  `stage_artifact_instructions` owns those, and §4.3 is what happens when a
  shared prompt disagrees with it.
- **A driver that can advance a stage,** by any route, including
  `relax_all(include_stage_gates=True)` and the domain command. §3.2.
- **Executing `LoopPolicy`, `Amendments`, `halt` or the rung ladder.** §3.4. Not
  a driver feature — new events, new commands, and an answer to what
  `current_stage` means during an outstanding amendment. A separate document.
- **Retry or convergence state held in the supervisor.** §3.4. That is
  `LoopPolicy` reimplemented where nothing can audit it.
- **Generators as subagents.** §3.3. `delegation.py` steers delegation toward
  investigation and warns specifically about subagents producing parts of a
  shared artifact. Critics yes; generators no.
- **A shared "objectives" prompt.** §4.4, and it is the most expensive idea in
  this document to get wrong.

### Open questions

1. **Who writes the prompts?** §8 is the whole answer and I cannot resolve it,
   because it is a question about the owner's time rather than about the code.
   Everything else here is contingent on it: a loader with nothing good to load
   is worse than no loader, because it makes the system look finished. **This is
   the one I could not resolve and the most expensive to get wrong.**
2. **Should a course built without critics be marked as such?** I think yes —
   the stage rail knows which stages declare a critic and could show that none
   ran — but it is a UI decision and §5 ships the increment either way.
3. **Should `StageAdvanced` gain a `decision` field now?** §6 argues it is the
   cheapest real signal about prompt quality and a clean case-1 addition
   (`decision: Decision = "approve"`, absence reading as the old behaviour). It
   is out of scope for a prompt library and it is the thing I would add next.
4. **Does the owner want `hybrid.default` first?** It is the default preset and
   the one a new project gets, so a prompt library that covers only `ubd.pure`
   leaves the default unrunnable. §5 recommends UbD anyway, on the grounds that a
   runnable six-stage preset beats an unrunnable fifteen-stage one, but the cost
   is that the first increment does not improve the default path and somebody has
   to choose UbD at project creation to see any of it.

## 11. Amendment: what may execute `AdvanceStage` (2026-08-09)

Appended rather than applied, per the `landing-page.md` §8 convention: §3.2's
reasoning is most of `stage-boundaries.md`'s foundation and stays readable
here. Where the two disagree, this section wins and says so by name.

§3.2 forbids a driver from calling `Project.execute(AdvanceStage(...))`
directly, on the grounds that the domain command is not gated and the tool is.
That is right about the hazard and wrong about where to close it.
`stage-boundaries.md` §4.4 works it through; the short form is that §3.2 closed
*who may execute the command* when the property that matters is *what must have
happened before the command is executed*, and those coincide only because the
tool is the sole caller today. The cost §3.2 does not price is that making the
tool the sole caller makes the **model** the only thing that can propose a
boundary — while the two facts that decide whether a stage is done,
`stage_artifact_paths` and `review_stage`, are computable and cost no model
call.

The amended rule, which `StageRunner` implements:

> **A component may execute `AdvanceStage` if and only if it has, immediately
> beforehand and in the same function, obtained an approval through
> `ApprovalPort` for that advance, or observed that the operator has set
> `advance_stage` to `auto`.** It may never write `AutonomyPolicy`. The
> prohibition in §3.2 is narrowed to this: the hazard was an advance with no
> decision behind it, not the identity of the caller.

Three things follow, and all three are enforced rather than asserted.

**The test §3.2 asked for is replaced by a stronger one.** §3.2 wanted "drive a
stage to completion and check no `StageAdvanced` was appended", which is the
right test for a rule about callers. The amended version is *no `StageAdvanced`
was appended without a corresponding approval*, which is strictly stronger and
is `test_no_stage_advanced_without_a_decision_recorded_against_it`. Beside it,
`test_advancing_is_only_reachable_through_the_function_that_asks` parses
`research_team/application/` and fails if a second construction site of
`AdvanceStage` appears, or if the one that exists stops calling
`ApprovalPort.decide` — because splitting the ask from the advance across two
functions would leave the second reachable without the first, and every
behavioural test would still pass.

**§3.2's corollary is narrowed, not deleted.** "A driver cannot finish a
course" becomes: a driver cannot finish a course *unless an operator has
already recorded that it may*. `relax_all(include_stage_gates=True)` is that
act — built, HTTP-routed, argued for at length in `autonomy.py`, and recorded
as `AutonomyChanged`. A runner that reads the policy is not creating the
capability; it is the first thing to use it. §3.2's honest options ("run a
shorter preset, or turn `advance_stage` to `auto` by hand and own the
consequence") were already the right ones and this changes only who acts on the
second.

**The unattended run still has a floor.** An invariant failure from
`review_stage` stops the run without asking anyone, at `auto` as well as at
`ask`, because `stage_exit.py` is right that there is nothing there for a human
to weigh either. So the two failures that would otherwise produce a course
claiming reviews it cannot evidence are not reachable by relaxing a policy.

What has **not** changed: §3.2's first route stays closed exactly as written.
The runner holds `AutonomyPolicy` and never calls `set` or `relax_all`, and
`test_the_runner_never_writes_the_autonomy_policy` fails if it does — including
if a constructor grows an `attended=` flag, which would be the same hole
through a different door. §3.4 is untouched: no `LoopPolicy`, no convergence
check, no retry state in the runner.

Open question 3 above is closed by the same work: `StageAdvanced.decision`
landed, as a case-1 addition, because a runner writing machine prose into
`gate_decision` leaves the human's verdict nowhere to live. Three of the five
`Decision` values are refused rather than stored, which keeps §3.4's
"unrepresentable" claim true instead of letting it become "representable and
meaningless".

## 12. Amendment: an unresolved ref degrades, it does not refuse (2026-08-09)

Appended rather than applied, same convention as §11. Where this disagrees with
§2.3, this section wins.

§2.3 says the composition root "should refuse to build with a preset whose
prompts it cannot resolve, and say which ref and which stage". §1's own premise
is why that cannot be the rule as written: the prompts were the thing that did
not exist, and §5 then plans a first increment — `ubd.pure`, generators only,
no critics — which is *by construction* a preset that does not fully resolve.
§2.3 and §5 were already in tension; the library on disk settles it. Six prompt
files exist against 38 distinct refs. `hybrid.default` is the default preset,
listed first because the order is the recommendation, and is missing 20 of its
22. `ubd.pure` has all six generator prompts and four `*_critique` refs that
resolve to nothing.

A build-time refusal against that library refuses all three presets. The wiring
would ship as an outage, and — the part that matters more — it would refuse
`ubd.pure`, the preset the six written prompts exist to serve.

The rule `prompting_for` implements instead:

> **Resolution is per stage, not per preset. A stage whose ref resolves runs
> under its prompt. A stage whose ref does not resolve runs under an explicit
> notice that names the missing ref and says the stage is running without its
> methodology.** A malformed or mis-`kind`ed prompt degrades identically; a
> library that will not *load* is still a startup failure.

The notice is the whole of why this is not the silent fallback §2.3 rejects.
That rejection is sound and is preserved: an ungated run is visibly ungated, and
a stage with an *empty* prompt is indistinguishable from the system before
prompts existed. A stage that tells the model, in band, that its methodology is
absent and asks it to say so in what it writes is not indistinguishable from
anything. It is §5's own answer for critics — "visibly labelled as such rather
than quietly equivalent" — applied to generators, which need it more, because a
missing critic subtracts a review and a missing generator subtracts the method.

**What this does not do, and should.** The notice is a request to a model, not
an enforcement. A degraded stage still writes artifacts and those artifacts
still pass `checks.py`, because the structural checks are graph queries over
`Intent` and cannot see which tradition wrote a node. Nothing yet records on the
*run* — as against on the turn — that a stage was worked unprompted, so a course
assembled from twenty degraded stages carries the fact only in the log. The
place for it is the stage rail §5 already points at, and the honest statement is
that this increment wires the prompt through and leaves the labelling of the
finished course undone.

`unresolved()` remains uncalled, for the reason §2.3 gave it a caller and the
library then withdrew: it returns a non-empty list for every shipped preset. It
stays the survey a prompt author reads, not a gate.
