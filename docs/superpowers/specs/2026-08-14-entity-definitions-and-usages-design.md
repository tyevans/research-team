# Entity definitions and usages

Clicking a node in the graph today gives you its name, its type, and a list
of edges. It does not tell you what the thing *is*, and it does not tell you
where in the corpus it was talked about. This adds both, to the panel that
already opens on click.

The definition is generated by an LLM, grounded in the passages that mention
the entity and in the edges the graph already holds, and cached until the
entity changes. The usages are the same passages, listed and citable. They
are one feature because they share their inputs: the retrieval that finds
what to show you is the retrieval that grounds what the model writes.

## What was verified before designing this

Three things were checked against source rather than assumed, because the
design turns on each.

**redstring already carries the whole retrieval stack, and this repo uses
none of it.** `ChunkStore`, `ChunkReader`, `ChunkProjection`, `ChunkId`,
`StoredChunk`, the `DocumentChunked` event, `index_documents`, and
`ChunkRetriever` are all in the 0.8.0 public surface. A grep across
`research_team/` and `tests/` returns zero hits for every one of them. So
this is wiring rather than building, in the same sense the temporal-edges
work was.

`ChunkRetriever.retrieve_chunks(query, tenant_id, k, mode)` does BM25 fused
with a cosine channel by reciprocal-rank fusion. `index_documents` makes no
LLM call unless an embedding provider is passed to it.

**`StoredChunk` knows its offsets.** `redstring/domain/chunk.py:78-94`:
`id`, `tenant_id`, `source_id`, `text`, `chunk_index`, `start_char`,
`end_char`, `entity_ids`, `metadata`, `embedding`. That `source_id` plus
those two integers are exactly the citation shape
`research_team/application/corpus_spans.py` already defines, which is what
makes Decision 2 below cheap rather than a compromise.

The same file documents that `ChunkId` is **content-addressed**: re-chunking
under different settings mints a new id rather than overwriting an existing
one. It also warns, in a docstring written to be read by exactly the person
about to make this mistake, that an empty `entity_ids` means no entities were
extracted from that passage and **never** means extraction is pending.
`index_documents` leaves it empty on every chunk it writes.

**Aliases are reachable and have never been read.** `AliasStore.find_aliases(
canonical_entity_id, tenant_id)` exists on the port. Nothing in this
repository calls it. The only alias machinery in use is `resolve_entity_ids`,
and it is used exclusively to filter aliases *out* —
`graph_reader.py:113-143`, called at three sites. Two constraints come with
`find_aliases`: it returns **direct** absorptions only, so a merge chain
needs recursion, and `Alias.alias_name` is `str | None` because the
projection folds `EntitiesMerged`, which carries ids and no names.

## Two decisions, and what was rejected

### Decision 1: usages are found lexically

`index_documents` runs with no embedding provider; `ChunkRetriever` is
queried in lexical mode.

A usage is a mention of a proper name. That is the case BM25 is built for and
the case embeddings are worst at — a semantically similar passage that never
mentions the entity is *not* a usage, and a hybrid index would surface it
confidently. Lexical-only also means indexing is deterministic, costs no
embedding pass over the corpus, and adds no model dependency to a code path
that currently has none.

Rejected: **hybrid retrieval**, for the reasons above plus the cost of an
embedding pass at index time. The retrieval mode is a parameter, so the
semantic channel can be switched on later — but note honestly that doing so
requires backfilling embeddings across every stored chunk, so "later" is a
migration, not a flag flip.

Rejected: **no chunk store at all** — an alias-aware scan of
`corpus_documents.text`, cut into passages by the existing
`corpus_spans.chunk`. It stores nothing and needs no projection, which is
genuinely attractive. It was rejected because it has no ranking, and ranking
is the difference between a usages panel and a wall of text; and because its
cost is linear in corpus size per click, on the request path.

One caution against a stale argument: `config.py:308-320` says embedding
`entity.name` "does not buy discrimination". That was written about
consolidation, where the embedded text is a bare name. It says nothing about
embedding passages, and should not be cited as if it did.

### Decision 2: a citation is `(source_id, start, end)`

The definition stores offsets, read off `StoredChunk.start_char` and
`end_char` at generation time. Not `ChunkId`s.

This keeps one citation shape in the system. `corpus_spans.py`'s module
docstring already states the premise — extraction discards offsets, so they
are re-derived on demand, and a citation is a source id plus two integers —
and `quote(text, start, end, *, context=0)` already exists to render one.
The `GET /api/projects/{id}/sources/{source_id}?start=&end=` route already
serves one.

The operational payoff is that the chunk index becomes disposable. Re-chunk
with different settings, drop the store, rebuild it — no citation a user has
already read is affected, because no citation refers to a chunk. Under
`ChunkId` citations, a chunker settings change silently orphans every stored
citation, and the definition cache would need a third invalidation trigger
beyond the two this design has.

The cost, stated plainly: we lose the ability to ask "which chunk did this
claim come from" after the fact, and content-addressed ids would have given
us that for free. If provenance-to-chunk is ever wanted, the fix is to store
the `ChunkId` *alongside* the offsets rather than instead of them.

## 1. Chunk index

New: `build_chunk_store()` in
`research_team/infrastructure/knowledge/stores.py`, beside the existing
`build_graph_store` and `build_vector_store` and following their env-switch
shape.

Chunking uses `BoundaryPreferenceChunker`, not the `SlidingWindowChunker`
that extraction uses (`composition.py:1209`). redstring's own docstring calls
it "the one to pass when the passages will be quoted back to a reader", which
is precisely this feature and precisely not extraction's problem.

**Two chunkers now exist over the same documents, and that is deliberate.**
Extraction's windows are sized for an LLM's attention
(`DEFAULT_EXTRACTION_CHUNK_SIZE = 2_000`, `config.py:36`); these are sized
for a human's. Unifying them would force one of the two jobs to accept the
other's boundaries. What must not happen is the two disagreeing about what a
*citation* is — and under Decision 2 they cannot, because neither owns
citation identity. Offsets into the source document do.

### The replay coupling, which is the sharp edge

`research_team/infrastructure/knowledge/rebuild.py:17` replays with
`strict=True` and a single projection. An unhandled event type fails project
open.

Once a `DocumentChunked` event exists in a project's log, `ChunkProjection`
must be registered at **every** site that opens that project — not only the
rebuild path. Miss one and existing projects stop opening entirely.

This fails loudly rather than silently, which is the good version of this
bug, but it fails totally. A test asserts that a log containing
`DocumentChunked` opens through every project-open path, and it must be
proven red by removing the projection registration before it is trusted
green.

Indexing is triggered where extraction is already triggered, on the
document-stored signal. It makes no LLM call, so it does not go through
`ExtractionQueue` and does not inherit B62's durability gap.

## 2. Alias resolution

New, small, in `infrastructure/knowledge/`. Given a canonical entity id,
return every name it is known by: its own `entity.name` plus the
`alias_name` of every `Alias` reachable from it.

Recursion is required — `find_aliases` returns direct absorptions only, so an
entity that absorbed an entity that had itself absorbed another needs the
chain walked. `alias_name` is skipped when `None`. The walk carries a seen-set
because nothing in the port's contract promises the alias graph is acyclic,
and a cycle here would hang a request rather than return a wrong answer.

Compare ids with `==` and never `is`. Both existing alias call sites carry
that warning (`graph_reader.py:113-143`, `redstring_adapter.py:736`) because
an adapter may hand back a rebuilt `UUID`.

## 3. The usages port

`research_team/application/` gains a port. No redstring type crosses it —
`tests/test_architecture.py:155-200` enforces that, and
`application/graph_read.py:184-191` states the intent.

```python
@dataclass(frozen=True)
class Usage:
    source_id: str
    start: int
    end: int
    text: str
    score: float
```

`usages(project_id, entity_id, *, limit)` in the adapter: resolve the alias
set, query `retrieve_chunks` in lexical mode once per name, fuse the results
by score, deduplicate by `(source_id, start, end)`, and read the offsets off
each `StoredChunk`.

Deduplication matters and is not incidental: an entity named "Acme
Corporation" with alias "Acme" will match the same passage under both
queries, and a usages list that shows the same sentence twice reads as a bug
to anyone looking at it.

## 4. Definition service and cache

`research_team/application/entity_definitions.py`.

Generation gathers the node's name, type and edges from the existing graph
reader, plus its top usages from the port above, prompts the extraction model
(one model, per the decision to add no second config knob), and returns text
with citations as `(source_id, start, end)` triples.

The prompt requires every claim to be attributable to a supplied passage or
to a supplied edge. A definition that cites nothing is a model talking about
what it already knew, which is the failure mode this feature exists to avoid
— the whole reason for grounding it was that an ungrounded gloss is
indistinguishable from a correct one at a glance.

The cache is a new read model in
`infrastructure/persistence/read_models.py`, following the
`CorpusDocumentRow` / `CorpusProjection` / `CorpusStore` / `CorpusRunner`
quartet, including a `rebuild()`. Row id is `uuid5` over
`f"{project_id}:{entity_id}"`, matching `CorpusDocumentRow.row_id`
(`read_models.py:649`).

Row fields: `project_id`, `entity_id`, `text`, `citations` (JSON), `model`,
`generated_at`, `stale`.

### Invalidation

A projection on that read model, subscribing to two redstring events.
`CorpusProjection._on_extracted` (`read_models.py:745`) is the working
precedent for a local projection folding a redstring event, including the
detail that it keys on `event.tenant_id` and skips a missing row rather than
raising.

- **`DocumentExtracted`** — mark `stale` on every cached definition whose
  entity id appears in `event.entities`. Entities never gain properties
  incrementally; a property change arrives as a whole-entity payload inside
  this event. So this one subscription covers the entire "more properties
  were added" case.
- **`EntitiesMerged`** — mark `stale` on `canonical_entity_id`, and delete
  the rows for `merged_entity_ids`. Those ids are no longer clickable; a
  cached definition for an absorbed entity is unreachable text taking up
  space, and leaving it would mean a `/rebuild` produces a different row
  count than steady-state operation for no reason anyone could explain.

Marking, not regenerating. Regeneration happens on the next click, which is
the behaviour asked for and also the cheap one: a bulk re-extraction that
touches two hundred entities would otherwise fire two hundred LLM calls for
definitions nobody has asked to read.

`MergeUndone` is deliberately **not** subscribed to, and this is a known gap
rather than an oversight. Undoing a merge restores entities whose definition
rows were deleted, so they regenerate on next click — correct. But the
canonical entity's definition is left marked stale from the original merge,
which is also correct, so no case produces a *wrong* answer. If undo ever
becomes common, the argument changes and this needs revisiting.

Rejected: **fingerprinting the inputs** and comparing on read. It would have
to read the entity and its chunks on every click to compute the fingerprint,
which is most of the work of answering the question, so it buys nothing over
letting a projection keep the books.

## 5. HTTP and the panel

Two endpoints, deliberately separate:

- `GET /api/projects/{project_id}/graph/entities/{entity_id}/usages`
- `GET /api/projects/{project_id}/graph/entities/{entity_id}/definition`

Usages are deterministic and cheap; a definition may cost an LLM call. One
combined endpoint would block the fast half on the slow half, and the panel
would sit empty for seconds holding data it already had.

Both follow the conventions in `app.py`: closures on the FastAPI instance
rather than an `APIRouter` (there are none in this codebase), first line
`await _require_project(project_id)`, a per-project reader helper that raises
503 when unwired and 404 for a missing row, and a plain dict from a `*_view`
function in `presenters.py`.

The definition endpoint generates **synchronously**. Extraction needs a queue
because it is long-running and losing a queued one loses an intention (B62);
a definition is seconds, idempotent, and re-triggered by the next click, so
the entire retry story is "click again". A durable queue here would be
machinery with no user-visible payoff.

`GraphDetail.tsx` gains two sections above the existing edge list. It is
already a non-modal `<aside>` closed by Escape via `useEscape`, and that does
not change.

A **stale definition is shown while a fresh one generates**, marked as
updating, rather than blanking the panel. The old text is still the best
answer available, and replacing it with a spinner makes the panel flicker on
every re-extraction for a change that may not affect the definition at all.

Query keys go in `frontend/src/application/queries/keys.ts` — there are no
graph keys there today, because the graph is a zustand store. That module's
docstring states the rule this must follow: keys are never spelled out at
call sites, because a misspelled invalidation silently does nothing.

## Testing

The four gates, all of them:

```
uv run ruff check .
uv run ruff format --check .
uv run pytest
cd frontend && npm run verify
```

Two obligations beyond the gates.

**The read model must be verified against a database that predates it.**
This adds a table and a projection; `apply_schema` is additive and
`CREATE TABLE IF NOT EXISTS` does nothing to a table that already exists.
Use the existing tool rather than copying the file:

```
uv run python -m research_team.infrastructure.persistence.local_copy /tmp/probe.db
```

It rewrites the store id in each checkpoint, which a plain copy does not —
a copied database raises `PositionForeignError` on open. Do **not** clear
`projection_checkpoints` to get it up: a projection with no checkpoint
replays the whole log, which is `/rebuild` by another name and hides the half
of the bug worth finding.

**Browser tests if any stylesheet or layout primitive is touched.**
`cd frontend && npm run test:browser`. jsdom lays nothing out, so a computed
style or a measurement asserted there is not asserted at all. Roles, focus
order, keyboard routing and rendered text stay in the jsdom suite.

Test-first throughout, and a test proven red before it is trusted green. Any
test that would pass with its change reverted says so in its docstring.

## Deliberately not in scope

- **Semantic retrieval.** Decision 1. Switching modes later requires an
  embedding backfill across stored chunks; it is not a flag flip.
- **A second model for definitions.** Considered and declined; definition
  generation uses the extraction model and `config.model_name()`.
- **Regenerating eagerly on invalidation.** By design.
- **`MergeUndone` handling.** Reasoned above: leaves no wrong answer today.
- **Chunk-level provenance on a definition.** Decision 2. Recoverable by
  storing `ChunkId` alongside the offsets if it is ever wanted.
- **Durability for anything here.** Nothing in this feature is an intention
  worth surviving a restart.
